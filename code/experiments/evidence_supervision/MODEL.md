# Qwen3-VL-4B-Instruct 구조

이 실험의 arm은 "이 모델의 어느 모듈을 학습하는가"로 정의되므로, 그 모듈이 무엇인지 정리한다. 출처는 고정 리비전의 `config.json`([`ebb281ec`](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct/tree/ebb281ec70b05090aa6165b016eac8ec08e71b17))과 파드에서 실측한 모듈 이름(`code/train/mmdl_trainable_spec.py`, 2026-11-19 probe)이다.

**검산**: 아래 모듈 형태에서 유도한 학습 파라미터 수가 실측값과 **정확히 일치**한다 — 언어 LoRA 132,120,576 / 어댑터 109,111,296 / 비전+어댑터 110,684,160. 구조 설명이 맞다는 근거다.

## 전체 그림

```
이미지 ──▶ 비전 타워 (24 블록, hidden 1024)
             │        │        │        │
          블록5    블록11   블록17   블록23(최종)
             │        │        │        │
             ▼        ▼        ▼        ▼
          deepstack_merger_list[0,1,2]   merger      ← 어댑터 4개 (각 27.3M)
             │        │        │        │
             └────────┴────────┴────────┴──▶ hidden 2560 으로 투영
                                              │
텍스트 ──────────────────────────────────────▶ 언어 모델 (36 층, hidden 2560)
                                              │
                                              ▼
                                        다음 토큰 분포 (vocab 151,936)
```

전체 파라미터 **4,569,936,384개**(약 4.57B), BF16.

## 언어 모델 — 36층

| 항목 | 값 | 비고 |
|---|---|---|
| 층 수 | **36** | `language_model.layers.0~35` |
| hidden_size | 2,560 | |
| attention head | 32 | head_dim 128 |
| key/value head | **8** | **GQA** — 쿼리 4개가 KV 1쌍을 공유 |
| FFN 중간 차원 | 9,728 | SwiGLU (`gate`·`up`·`down`), 활성 `silu` |
| vocab | 151,936 | `tie_word_embeddings = true` — 입력 임베딩과 출력 헤드가 **같은 가중치** |
| 위치 인코딩 | M-RoPE, `rope_theta` 5,000,000 | `mrope_section [24,20,20]` = (시간, 높이, 너비)로 head_dim/2=64를 쪼갬 |
| 최대 길이 | 262,144 | 우리는 학습 2,048 / 평가 8,192로 제한 |

**GQA가 LoRA 비용을 비대칭으로 만든다.** head_dim 128 × 32 head = 4,096이라 `q_proj`는 2560→**4096**(정사각이 아니다), `k_proj`·`v_proj`는 2560→**1024**(KV head 8개뿐), `o_proj`는 4096→2560이다. 그래서 같은 rank에서도 q·o가 k·v의 약 1.9배 비싸다.

층당 모듈: `self_attn.{q,k,v,o}_proj` + `mlp.{gate,up,down}_proj`.

## 비전 타워 — 24 블록

| 항목 | 값 | 비고 |
|---|---|---|
| 블록 수 | **24** | `visual.blocks.0~23` |
| hidden_size | 1,024 | 언어 쪽 2,560보다 작다 |
| head | 16 | head_dim 64 |
| FFN 중간 차원 | 4,096 | 활성 `gelu_pytorch_tanh`, SwiGLU 아님 (`linear_fc1`·`linear_fc2`) |
| patch | 16×16, 시간 2 | 입력 채널 3 |
| spatial_merge | 2 | 2×2 패치를 토큰 1개로 합침 |
| out_hidden_size | 2,560 | 언어 hidden과 맞춤 |
| 위치 임베딩 | 2,304개 | 48×48 격자를 보간해 씀 |
| **deepstack 탭** | **블록 5, 11, 17** | 아래 참조 |

**attention이 융합형이다.** 언어 쪽은 q/k/v가 별도 Linear인데 비전 블록은 **하나의 `qkv`**(1024→3072)와 `proj`(1024→1024)다. 그래서 arm 설정에서 비전 타깃 이름이 `qkv`·`proj`이고 언어 타깃이 `q_proj`… 로 다르다.

### patch_embed — 100배 가속의 현장

입력 패치는 `(패치수, 3, 2, 16, 16)`이고, 이것이 `nn.Conv3d(3, 1024, kernel=(2,16,16), stride=(2,16,16))`을 통과한다. **커널과 입력 범위가 같아서** 출력이 `(패치수, 1024, 1, 1, 1)`이다. 즉 이 합성곱은 수학적으로 `(N, 1536) @ (1536, 1024)` 행렬곱이다(3×2×16×16 = 1,536).

cuDNN이 이 모양에서 병리적인 알고리즘을 골라 학습이 **174.5초/step**이었고, 같은 연산을 행렬곱으로 바꿔 **1.77초/step**이 됐다(비트 단위 동일, `max abs diff 0.000e+00`). 비전 타워 전체 forward 10,852 ms 중 patch_embed가 **99.8%**였다. 같은 가중치로 vLLM이 빠른 이유도 이것이다 — vLLM은 여기서 Conv3d를 쓰지 않는다. 구현은 `code/train/patch_embed_fix.py`.

### 시각 토큰 환산

패치 16×16에 spatial_merge 2이므로 **토큰 1개가 32×32 = 1,024 픽셀**을 담는다.

| | min_pixels ~ max_pixels | 이미지당 토큰 |
|---|---|---|
| 평가 | 262,144 ~ 2,097,152 | **256 ~ 2,048** |
| 학습 | 65,536 ~ 524,288 | **64 ~ 512** |

학습 해상도를 낮게 둔 건 역전파 메모리가 추론보다 크기 때문이다. 발표에서 "왜 학습과 평가의 해상도가 다른가" 질문이 나오면 이 표가 답이다.

## 어댑터 — DeepStack이 핵심

**이 모델에서 비전→언어 연결은 한 갈래가 아니라 네 갈래다.**

보통의 VLM은 비전 타워 **최종 출력**만 투영해 LLM 입력 앞에 붙인다. Qwen3-VL은 거기에 더해 **중간 블록 5, 11, 17의 출력을 따로 빼내** 각자의 투영기를 거쳐 LLM에 주입한다(`deepstack_visual_indexes = [5, 11, 17]`). 저수준 시각 특징과 고수준 특징을 함께 쓰려는 설계다.

그래서 투영기가 4개다.

| 모듈 | 역할 |
|---|---|
| `visual.merger` | 최종 블록(23) 출력 투영 |
| `visual.deepstack_merger_list.0` | 블록 5 탭 |
| `visual.deepstack_merger_list.1` | 블록 11 탭 |
| `visual.deepstack_merger_list.2` | 블록 17 탭 |

**네 개가 완전히 같은 형태**이고, 각각 이렇게 생겼다.

```
입력 = spatial_merge² × hidden = 2×2 × 1024 = 4096
  LayerNorm(4096)                       8,192
  linear_fc1  4096 → 4096          16,781,312
  linear_fc2  4096 → 2560          10,488,320   ← 언어 hidden으로
                                   ──────────
  merger 1개                       27,277,824
  × 4개                           109,111,296   ← arm C1이 학습하는 전부
```

**이 109.11M이 왜 중요한가.** arm C1은 LLM과 비전 인코더를 완전히 동결하고 이 네 투영기만 **전체 학습**한다. 즉 "비전이 본 것을 언어로 넘기는 통로"만 고치는 실험이다. 그런데 결과가 **정확히 0.00pp**(회복 46 / 퇴행 46, p=1.0)였다. 통로의 용량이 작아서가 아니다 — 109.11M은 언어 attention LoRA(r=64, 47.19M)보다 **2.3배 크다.** 통로를 통째로 다시 배워도 아무것도 바뀌지 않았다는 뜻이고, 이게 발표 RQ1에 대한 직접적인 답이다.

## arm이 무엇을 학습하는가

| arm | 학습 대상 | 파라미터 | 전체 대비 |
|---|---|---|---|
| **A** / **B** | 언어 LoRA r=64: 36층 × (`q,k,v,o` + `gate,up,down`) | **132,120,576** | 2.89% |
| **C1** | 어댑터 4개 전체 (LoRA 아님) | **109,111,296** | 2.39% |
| **A′** / **C2** | 비전 블록 20–23 `qkv`+`proj` LoRA + 어댑터 전체 | **110,684,160** | 2.42% |
| **D** | A + C2 | 242,804,736 | 5.31% |

언어 LoRA 132.12M의 내부 구성:

```
층당 attention q,k,v,o      1,310,720   (q 425,984 · k 229,376 · v 229,376 · o 425,984)
층당 mlp gate,up,down       2,359,296   (각 786,432)
                           ──────────
층당 합계                    3,670,016
× 36층                    132,120,576
```

비전 블록 LoRA는 블록당 `qkv` 262,144 + `proj` 131,072 = 393,216이고, 상위 4블록이면 1,572,864다. 어댑터 109.11M에 비하면 **1.4%**라서, A′/C2의 학습량은 사실상 어댑터가 전부다.

> **arm 간 용량이 맞지 않는다.** 언어 attention LoRA는 rank 1당 0.737M이므로 어댑터 109.11M에 맞추려면 rank가 약 148이 필요하다(비현실적). 그래서 arm 비교에는 **점수와 함께 학습 파라미터 수를 항상 같이 적는다.** 계산은 `python code/cluster/count_trainable.py <모델경로>`.

## 상류(upstream) trainer를 왜 패치했는가

Qwen 공식 멀티모달 trainer의 LoRA 분기는 `target_modules=["q_proj","k_proj","v_proj","o_proj"]`를 **하드코딩**하고 층 선택도, 비전 경로도, `modules_to_save`도 없다. 그 분기로는 arm A와 B(언어 attention)만 도달 가능하다. 그래서 `code/train/patch_lora_branch.py`가 그 분기를 `code/train/mmdl_trainable_spec.py`의 `apply()` 호출로 바꾼다. arm 정의는 `configs/arms/*.toml`의 `[trainable]` 섹션에서 JSON으로 전달된다.

구조를 직접 확인하려면 `python code/cluster/inspect_structure.py <모델경로>`.
